**《安德鲁牙科连锁系统分析与设计_最终提交版.docx》（开发基线 V1.2）是唯一母本，一切以它为准。**

## 2. 母本：最终提交版

### 2.1 它是什么

这是本课程作业的最终交付文本，覆盖从愿景到数据库设计的完整链路：

- 第一章 愿景：现状、目标组织、指标及事实来源；
- 第二章 业务建模：业务用例（预约就诊、接受诊疗、结算缴费、经营与绩效监督）、现状与改进业务序列图；
- 第三章 需求：系统边界与角色（表 3-1）、7 个系统用例 UC01–UC07 及规约、预约金规则（表 3-2）、横切需求与验收条件（表 3-3）；
- 第四章 分析：分析类图、序列图、8 个状态机（图 4-10 至 4-17）、领域不变式 I01–I13；
- 第五章 设计：四层架构与模块（表 5-1）、类到关系映射、整库与分区 ERD、数据字典约定、事务与并发、经营统计与季度绩效、角色界面（表 5-4）、验收矩阵（表 5-5）；
- 附录 A：40 张 PostgreSQL 表的字段、类型、默认值、键与行内约束；
- 附录 B：业务到系统、模型及关系设计的追踪表（表 B-1）；
- 附录 C：R01–R09 已确认条款、最小可见字段和对应的服务验收。

### 2.2 它的权威地位

- 它是**需求的唯一出处**。任何功能、字段、状态、角色、规则、参数，都必须能在提交版中找到对应条目。
- 它是**验收的基准**。验收时逐条对照提交版，而不是对照开发者的理解、旧稿或聊天记录。
- 它是**变更的起点**。需要改变业务时，先改提交版（经作者确认），再改系统；不允许“系统先做了再说”。
- 辅助资料只能用来**理解**提交版，不能用来**覆盖**提交版。

## 3. 辅助资料一：业务细节与开发说明书 V1.0

### 3.1 它的作用

这份文件是提交版形成之前的**内部上下文基线**，价值在于：

- 记录原始案例事实（标注 `[原始]`）与用户已确认的决策（标注 `[确认]`）；
- 汇总 18 条核心决策 D01–D18 和首期可配置参数（如预约金 50 元、占位 10 分钟、24/2 小时退款档位、7 天预约窗口等）；
- 列出历史 100 页旧稿中**不可继承**的做法（如无预约直接接诊、按排班工时分摊、自动个人分奖等）；
- 给出当时的技术倾向、待核实事项（P0–P2）和建模规范摘要。

### 3.2 它不能做什么

- **不能替代提交版。** 它的自述明确写着“不是已完成的课程报告”，且部分内容标注 `[建议]`、`[待核实]`，不是已批准的最终需求。
- **不能覆盖提交版。** 已知至少两处与提交版不一致，必须以提交版为准：
  1. **业务用例数量**：基线 2.1 节曾要求固定为 3 项；提交版表 2-1 最终采用 4 项，增加“经营与绩效监督”，并把总部作为内部监督服务接收角色。以提交版为准。
  2. **技术栈**：基线 13.1 节倾向 FastAPI + Vue 3 + MySQL；提交版 5.1 节定为 Django/Python + React Web + 微信原生小程序 + PostgreSQL。以提交版为准。
- **不能当作进度承诺。** 基线中的“当前进度”是 11-19 的状态，提交版 11-21 已经补齐第三至五章和附录。

### 3.3 正确用法

只有在提交版表述较简、需要补充背景或解释口径时，才查阅基线；一旦两者不一致，立即回到提交版，并把差异记入变更登记。

### 4.2 它的地位

提交版 5.4 节写明“附录 A 与独立 PostgreSQL 脚本同源”。但本目录中的这份草案是 **11-19 的早期稿**，早于 11-21 的提交版，已出现漂移。**它不是权威结构，不能直接拿来建库上线或作为验收依据。**

### 4.3 已发现的漂移（示例，非穷尽）

| 项目 | 11-19 草案 | 11-21 提交版（附录 A） | 处理 |
|---|---|---|---|
| `employee_role` 唯一约束 | `UNIQUE (employee_id, role_id, scope_clinic_id)` | `UNIQUE NULLS NOT DISTINCT (...)` | 以提交版为准 |
| `appointment.is_attended` 约束 | `NOT is_attended OR status IN (...)` | `is_attended = (status IN ('IN_TREATMENT','COMPLETED'))` | 以提交版为准 |
| `appointment_change` | 缺少操作者二选一、改期新旧占位等 CHECK | 含 `num_nonnulls` 与改期新旧占位校验 | 以提交版为准 |
| `visit` | 缺少中止原因必填校验 | `TERMINATED` 必须填写中止原因 | 以提交版为准 |
| `treatment_item` | 无 `is_additional`，无患者同意校验，无金额公式校验 | 有 `is_additional`、`NOT is_additional OR patient_consented`、`amount=ROUND(units*unit_price_snapshot,2)` | 以提交版为准 |
| `invoice.status` | 枚举含 `VOIDED`（4 值） | 仅 `ISSUED/PART_PAID/SETTLED`（3 值） | 以提交版为准 |

| `invoice_payment` | 无 `adjustment_id` 及关联索引 | 有 `adjustment_id REFERENCES invoice_adjustment(id)` | 以提交版为准 |
| 外键数量 | `REFERENCES` 子句 62 处 | 5.9 节称 64 条外键 | 以提交版为准 |

## 5. 系统与提交版的一一对应原则（核心）

### 5.1 对应关系是双向的

| 方向 | 要求 | 含义 |
|---|---|---|
| 提交版 → 系统（完整性） | 提交版中所有可实现的系统内容，系统都必须实现并可验收 | 7 个系统用例、角色权限、业务规则、状态机、40 张表、界面入口等，不能漏做 |
| 系统 → 提交版（纯净性） | 系统里所有面向用户的功能、数据、规则、状态、角色、参数，都必须在提交版中有出处 | **系统有的东西，usecase 里面一定要有**；不得私自增加功能、表、字段、状态或规则 |

“一一对应”不是“大致相似”，而是：**每一个系统要素都能指到提交版的具体条目；每一个提交版系统条目都能指到系统的实现和测试。**

### 5.2 按粒度对应

| 系统要素 | 必须对应的提交版锚点 | 验收证据 |
|---|---|---|
| 每个系统用例 | UC01–UC07（3.3 节）及表 B-1 | 用例实现 + 场景测试 |
| 每个角色及其操作范围 | 表 3-1、表 5-4 | 权限测试（正例/反例） |
| 每条业务规则 | 表 3-2、表 3-3、第五章各节、附录 C | 规则测试（边界值） |
| 每条领域不变式 | I01–I13（表 4-3） | 并发/约束测试 |
| 每个状态与迁移 | 图 4-10 至图 4-17 | 状态机测试，无额外状态 |
| 每张表、字段、约束 | 附录 A（A.1–A.40）、5.2–5.4 节 | DDL 与附录逐项核对 |
| 每个模块 | 表 5-1 | 模块清单与代码目录一致 |
| 每个界面入口 | 表 5-4 | 页面路径与范围校验 |
| 每个验收场景 | 表 5-5 | 验收记录 |
| 每个数值参数 | 表 3-2、表 5-3（50 元、10 分钟、24/2 小时、10%、Asia/Shanghai 等） | 配置值与测试用例 |

### 5.3 纯技术实现的边界

框架、部署、日志实现、缓存、构建工具等**不改变业务行为的纯技术选择**，不需要在提交版中逐条出现；但它们：

- 不得新增任何用户可见的功能、字段、状态、角色、规则或参数；
- 不得改变提交版规定的接口入口、数据口径或权限边界；
- 一旦产生了业务语义（例如新增“自动爽约”任务、新增“个人奖金”字段），就必须先补进提交版，再开发。

一句话：**技术实现可以自由，业务内容不能多也不能少。**

### 5.4 明确禁止的“系统多出来”

- 增加第 5 个业务用例，或增加 UC08 及以后的系统用例（除非先改提交版）；
- 增加附录 A 之外的表、字段、状态枚举或角色；
- 启用提交版已停用的“自动爽约”；
- 把公司激励基金分配到个人，或新增个人奖金公式；
- 对接真实医保、真实支付或写入真实患者数据；
- 实现提交版标记为“待核实/未确认”的家庭成员代约等规则；
- 继续采用基线中的旧技术栈，或直接执行 11-19 的 SQL 草案；
- 以“优化”“补全”为名，悄悄改变取消/退款、分摊、归期等业务口径。

### 5.5 冲突与变更流程

1. **发现差异**：开发、测试或评审中发现系统与提交版不一致，先登记，不直接改代码。
2. **判定依据**：提交版优先；辅助资料与提交版冲突时，按提交版执行。
3. **确需变更业务**：先修改提交版（由作者确认版本），再同步修改系统、DDL、测试和追踪表。
4. **同步范围**：提交版 → 基线（如仍维护）→ SQL/DDL → 验证脚本 → 接口与界面 → 测试用例 → 追踪矩阵。
5. **关闭条件**：追踪矩阵中该条目双向可追溯，测试通过，变更记录归档。
