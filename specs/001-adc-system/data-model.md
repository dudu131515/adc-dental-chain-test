# ADC 数据模型

[统一规约](spec.md) · [技术方案](plan.md) · [API 契约](contracts/api.md) · [现行设计 SQL](../../usecase/ADC_PostgreSQL_设计与统计.sql) · [验证 SQL](../../usecase/ADC_PostgreSQL_验证.sql)

业务库沿用 V1.2 附录 A 的 40 张表、268 个字段、70 条外键、4 个视图。下文的字段、约束和索引按现行 SQL 展开。Django 映射保留表名、列名、精度、空值、组合关系和约束，R01–R09 的联动与授权由业务事务约束。

## 领域与关系

| 领域 | 主体及关系 | 追溯 |
| --- | --- | --- |
| 身份和范围 | `user_account` 只关联一个员工或患者。员工可经 `employee_role` 拥有多个权限范围，空门店范围仅用于获授总部权限的角色。通过相关记录定位门店或履职主体。审计关联操作者与业务目标 | FR-001 至 FR-005、AC-X-01 |
| 排班项目与资源 | 诊所拥有牙椅、停用区间和排班需求。牙医经任职资格关联有效证书，需求可对应多个班次。项目保存资格、默认时长及椅型，与多条连续或间断但不重叠价格版本关联 | FR-101 至 FR-104、FR-201 至 FR-203、FR-501 至 FR-503 |
| 预约与预约金 | 占位关联患者、门店、牙医、班次和主项目。正式预约对当前占位及原预约金均唯一，原预约金指向初次占位。改期保留旧新占位，预约可有多条意向项目和操作事件。退金记录独立关联原款 | FR-201 至 FR-210、I01 至 I05 |
| 接诊与治疗 | 预约至多有一个实际就诊，椅位变更带来多条实际使用记录且在同一刻最多一条开放记录。就诊关联工作计时和治疗项，治疗项与耗材使用为一对多，数量及金额使用快照 | FR-301 至 FR-308、I06 至 I08 |
| 结算与更正 | 就诊至多有一张主单，原始明细每个治疗项至多一行且必须属于同次就诊。一个更正申请至多一次审批与一次差额。收退关联主单，退款逐笔指向成功原收款，可关联差额 | FR-401 至 FR-408、I09 至 I11 |
| 经营与绩效 | 运营费用归门店与季度，按直接或共同规则归属。有分摊的费用可对应多名牙医。每期每版按牙医及门店唯一保存贡献、公司结果每版唯一，修订键为 `(period_id, revision_no)` | FR-601 至 FR-605、FR-701 至 FR-707、I12 至 I13 |

## 数据生命周期与状态

| 对象 | 状态来源与迁移 | 必要联动 |
| --- | --- | --- |
| 班次 | `DRAFT → PENDING → ACCEPTED → PUBLISHED`。拒绝进入 `REJECTED` 后重新拟排，撤销为 `CANCELLED` | 只用已发布班次供给预约。资格、回应、冲突、跨店间隔和受影响预约协调在发布或撤销事务内重查 |
| 占位 | `HOLD → CONFIRMED / EXPIRED / RELEASED`，正式占位履约结束或业务变更可释放 | 到期按服务时间判断，原预约金不随当前占位移动。改期的成功状态与释放旧位、审计原子写入 |
| 预约 | `CONFIRMED → CHECKED_IN → IN_TREATMENT → COMPLETED`。前置条件合法时可进入 `CANCELLED` 或按人工核实进入 `NO_SHOW` | `is_attended` 仅在实际接诊或履约结束为真。先签到再分椅可保持已签到，待分椅是界面动作提示 |
| 预约金／退金 | 预约金 `PENDING / PAID / FAILED`。退金 `PENDING / SUCCEEDED / FAILED / RETAINED` | 相同业务键保留同一义务，成功结果不退回失败；晚到的可核验成功不创建已释放预约。退款失败可重试已有义务 |
| 就诊 | `IN_PROGRESS → COMPLETED / TERMINATED` | 开始时唯一就诊与退金义务一起提交。完成须有实做项目，中止须有原因，计时结束并释放资源。中止的预约仍为已履约 |
| 主单／资金 | 主单 `ISSUED / PART_PAID / SETTLED`。收退种类 `PAYMENT / REFUND`，各自 `PENDING / SUCCEEDED / FAILED` | 主单由应计和成功净收计算，足额为已结清，超收保留应退余额并展示在途状态。待处理资金不计入净实收 |
| 更正 | `PENDING → APPROVED → APPLIED`，或 `PENDING → REJECTED` | 已获批且属于同一就诊及主单才可入账，重复返回既有差额 |
| 季度及版次 | 季度 `OPEN → CALCULATING → REVIEW → CONFIRMED`，缺项 `NEEDS_DATA` 后补证据重算。复核退回重算。已确认季度继续保持 `CONFIRMED` | 修订确认人及确认时间一起赋值。正式报表用最新确认版，首次和历史版本保留。修订中的待复核状态从该版确认记录导出 |

现行 SQL 对 `clinic.status`、`shift_demand.status`、`dental_chair.status`、`user_account.status` 规定默认值并保持文本列。应用按母本允许的动作更新和读取这些列，状态词及迁移以原图和规约为准。

## 现有审计载体用于补齐业务证据

| 事件 | 目标及允许的最小业务内容 | 一致性和访问 |
| --- | --- | --- |
| 预约改期／取消、爽约、路线复核或牙医回应 | 指向预约、变更或班次，关联旧新资源、操作理由、责任、同意或路线核验结论、核准日历版本及提交时点 | 与变更一起保存，已确认变更由管理网站按门店与操作权回查 |
| 复杂项目估时、签到分椅及治疗见证 | 指向占位、预约、就诊或治疗项，保存原业务编号、牙医估时依据与分钟、椅位变更、患者同意／拒绝。实做治疗事件保存实际实施时点、项目名和有效价格版引用、耗材单位成本凭据引用 | 追加拒绝保留证据，无 treatment_item 计费行。同意事件与实际执行项关联。开单引用治疗时的名称、单位、价格和数量快照。临床证据按责任关系访问 |
| 模拟原付款与退款路径 | 指向原资金记录，保存模拟支付路径引用、可核对的回执标识、请求目标、规范化金额及幂等输入摘要 | 回执确认和流水更新同事务写入。审批和资金凭据可授权核对，客户端令牌和秘密不进入载荷 |
| 费用及季度版本 | 指向 `operating_expense` 或 `performance_revision`，保存费用凭据引用、计算的应计来源及版本、实际分钟、费用分摊与未分配证据、确认理由和结果 | 试算及确认有审计证据。首次确认后冻结原输入及结果，修订保存递增快照。已确认季度复算从该版证据取数，即使费用实时视图或其他草案改变 |

`audit_log.before_value`／`after_value` 按事件版本化和字段白名单序列化，冻结记录追加事件表达变更。取消核实与处置、诊疗退款的冲突及核对结论均关联原业务义务。跨店后原店按旧占位和本店资金引用回查该店已产生事实，目标店按当前占位履约。授权投影采用 Spec 最小字段表，通用日志仅记录请求关联号与结果。

## 事务一致性与视图

- 区间校验以 PostgreSQL 排他约束为安全网。跨店相邻间隔、容量、患者与初次支付关联、操作范围、同一主单收退限额、分摊和冻结不能由单行约束表达，按 [技术方案的事务设计](plan.md#关键事务与一致性) 实施。
- 金额使用 PostgreSQL `NUMERIC` 和 Python `Decimal`，计费行四舍五入到分，单位数量按 SQL 指定精度，实际分钟按实时时差。共同费用按同店同季度实际分钟比例分摊，每份向下保留到分，未分配为费用减分摊合计。全段实际分钟随就诊结束所在季度。接口以十进制字符串传输金额。
- 时点用 `TIMESTAMPTZ`，日历日期用 `DATE`。展示、改期工作日和季度归期采用 Asia/Shanghai。占位起止、当前预约、到诊、就诊时段、付款时点、统计截止和季度确认分别取源。
- `appointment_reporting_fact` 连接已支付正式预约的当前占位，包含其本地服务日期及时段结束。服务以 `slot_end_at <= as_of` 筛选，分组和下钻复用同一范围。
- `invoice_reporting_fact` 汇总原额、已入账差额、成功收退、欠款与应退，区分应计和资金。授权时以它关联的就诊回到发生门店和牙医。
- `expense_reporting_fact` 提供费用、现行分摊及未分配。已确认版精确复核使用该版本冻结的计算证据。
- `company_performance_revision_fact` 给出原值、版次、确认时点和差额；UC06 筛选 `confirmed_at IS NOT NULL`，授权核算仍可查看草案。
- 技术库 `adc_runtime` 只承载 Django 会话、短期 report scope 快照与框架迁移记录，与业务库/业务表分别验证。员工密码哈希配置、已批准门店工作日历版本和平台凭据由运行环境供应。业务库初始化不运行会话或权限框架建表。

## 工作台与患者连续服务投影

工作台按现有预约状态、当前占位门店及开始时点汇总。A.10 患者经当前预约归属或 A.37 前台登记事件确认关联门店，由本店前台读取最小身份、电话和本店预约投影。

A.11 PatientAllergy 保存当前已知过敏。A.37 追加 PATIENT_ALLERGY_REVIEWED，保存患者、操作者、预约、时间、结果和变更条目 ID。患者行锁串行化同一患者的确认，最新核对事件 ID 为版本，首次为 0。业务库应用角色可新增、修改及删除 patient_allergy。通用审计为追加权限。
