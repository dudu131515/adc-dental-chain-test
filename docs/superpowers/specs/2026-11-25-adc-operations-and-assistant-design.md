# ADC 业务补齐与经营分析助手设计

已确认设计。2026-11-25。用户选定 B，并确认工作台只显示红点。经营助手继续提供可选择的分析建议。

## 目标

ADC 保留一个员工管理网站、一个患者微信原生小程序、一套 Django API 和 PostgreSQL。扩展范围围绕一个可复现的课程验收流程。患者预约，前台分椅签到，牙医核对过敏并完成治疗，前台办理模拟收退并日结，患者查看本人的诊疗费用，总部在同一经营报表中使用 DeepSeek 分析两店结果。

本次范围包括导航重组、工作台待处理、门店与员工权限入口、日结对账、患者费用单、双店演示数据和经营 Agent。候补、主动微信推送、复诊回访、患者就诊摘要发布、完整电子病历、牙位图、库存管理和真实支付作为后续业务议题。演示期间使用合成样例和模拟资金。

参考 [CDC Manager 的工作台与岗位入口](https://www.orlandopedrazzoli.com/work/cdc-manager)、[ADC 现行 UI 设计](2026-11-22-adc-product-ui-design.md) 和[业务规约](../../../specs/001-adc-system/spec.md)。既有 [经营报表接口](../../../backend/adc/reporting/operations_api.py) 提供统计期间、截止、范围和授权明细，可供 Agent 复用。

## 导航与操作入口

网站采用左侧纵向主导航，业务页面使用顶部页签。页面默认打开当前账号可办理的入口。切换页签和从待办进入详情保留已选门店、日期及可用筛选条件，历史路径按原有权限指向相应页面。

| 主导航 | 顶部页签和主要操作 |
| --- | --- |
| 工作台 | 保留现有工作台和快捷入口。在对应入口显示红点，进入既有页签办理。 |
| 排班与预约 | 预约日历、班次、牙椅资源。原停诊协调和预约变更由现有详情继续办理。 |
| 患者与诊疗 | 患者档案、候诊与接诊、诊疗记录。前台按本店进入档案，牙医按履职进入临床视图。 |
| 收费与经营 | 结算、日结对账、经营报表、季度绩效。经营报表内打开分析助手。 |
| 基础管理 | 门店、员工与权限、项目与价格。各页签独立鉴权。 |

小程序保留首页、预约、我的三个主入口。在「我的」增加「诊疗费用单」，有已开立主单的本人预约详情显示同一入口。预约金和诊疗费用分别显示。

## 业务补齐

### 工作台待处理

从现有业务状态派生按权限过滤的布尔提示。工作台只在已有可访问入口旁显示红点，读屏可获取待处理提示。点入口进入现有业务页面，后者承接进度和办理。

- 前台看本店待接诊名单、到期未处置的预约、待开立主单和有权核对的未决资金。待开单以已结束或中止且尚无主单为准，办理条件仍由现有结算服务判定。
- 责任牙医看本人已签到或进行中的工作。诊所主管看本店待审批更正。待审批状态沿用更正服务。
- 现有接诊、结算及更正页面继承原排序与办理方式。工作台提示从真实状态推导，已处理事项从红点条件移除。
- 提示只表示是否存在有权处理的事项。跨店撤权后，下一次读取及办理立即按现行权限校验。

### 门店、员工与权限

基础管理为同一管理网站内的受保护入口。首版以预设角色、员工业务状态和范围授权为边界。

- 门店页提供已配置门店与基本业务资料查询。现有排班和运营配置继续由所属业务页签维护。
- 采用单独的总部权限管理职责，由部署初始化指定。管理员读员工和账号的最小资料，启停已有员工账号、按角色规则赋予或撤销门店范围。首次凭据由现有部署初始化提供。拥有该权限管理职责只授予权限后台能力，临床、财务和经营仍由各自角色授权。
- 后台可为其他现有员工分配或撤销诊所前台、牙医、诊所主管、总部排班、项目与价格管理、经营查询六个预设角色。每笔授权绑定一间明确门店，需要多店时分别授权。无门店限定的总部授权、季度核算／复核／确认权限、总部权限管理职责及其账号启停由部署配置维护。后台服务端拒绝自我授权，并保护管理职责及最后一个有效管理员。
- 每次变更在数据库事务内锁定受影响的授权目标及共同约束，重读操作者当前授权。审计记录操作者、目标、变更时间、原因和角色范围前后值。重复提交复用既有结果；并发修改旧状态提示重新查询。
- 扩展同源 SQL、初始化和最小数据库权限脚本。由受限应用账号验证正常操作和越权拒绝。员工旧会话每次请求重查账号和授权，撤权从变更提交后的下一次请求起生效。

### 日结与对账

前台读有权办理门店，主管读授权本店。选定 Asia/Shanghai 营业日期及门店，以同一次一致性读取显示以下事实。

- 预约金实收、预约金已退、诊疗已收及诊疗已退按成功回执的本地日期纳入。原款、退款、净额分列。诊所原因、患者原因和留存可回查来源，留存不作为一笔新增现金流。
- 未决区显示查询截止时已发起且尚在途的义务，使用首次发起时间标注跨日，重试沿原义务及首次发起日。优先读取现有请求时间或发起审计时间。旧数据缺发起证据时列为「发起时间待核实」。历史日视图明确标识未决区按本次查询截止读取。本版日结为核对视图，业务款项仍由原流程处理。
- 逐笔核对可见资金编号、归属门店、类型、金额、状态、首次发起和回执时间及授权范围内的关联标识。原详情已有权限时才显示跳转。否则在日结页展示同店最小资金证据，跨店改约的原店复用现有交接凭据。预约金资金归首次占位门店，诊疗款归主单来源就诊门店。未转正退金可用原占位关联的最小资金证据核对。

### 患者诊疗费用单

仅由患者会话从本人的已开立主单读取最小费用投影。显示主单号、原就诊日期、门店、冻结计费项目、当前应缴、成功收退款、欠款和正在进行的退款。已获批且入账的差额单独显示。使用独立患者查询权限和分页，详情按患者所有权查找。支付业务仍由当前课程模拟流程承接，费用单作为本人核对入口。

## 经营分析助手

### 用户主动选择

在「收费与经营 → 经营报表」的当前门店、期间和权限上下文中，放置「经营分析助手」。打开时展示三至四个可点击的建议。点击把指标与期间带入可编辑的查询，用户确认后开始分析。同一对比方案可改门店、时间和指标。内容由可用指标、门店授权及已生成结果决定。

| 建议 | 可用条件 | 选择后带入 |
| --- | --- | --- |
| 对比两家门店本周和上周的实际就诊率 | 当前账号有至少两家门店的经营查询权限 | 已授权门店、两个本地期间、就诊率。 |
| 看哪些门店到期未处置较多 | 有经营查询权限 | 当前范围、到期未处置数及共有分母。 |
| 本期诊疗净实收为什么变化 | 有经营查询权限 | 汇总收款、退款、净实收及对比期间，呈现数值构成。 |
| 查询预约金退还规则 | 有经营查询权限 | 已确认的预约金制度条款及版本引用。 |

完成后继续给可选的下一步。已显示到期未处置时建议「查看同范围异常明细」。退款变化时建议「查看收退构成」。数据缺失或零分母时建议「换一个期间」或「查看统计口径」。用户看到的建议仅来自可执行动作，展示建议本身不触发模型请求。展示前先用角色与范围过滤。

### 查询、工具与展示

1. 小程序继续面向患者。助手由网站上具备现有经营查询能力的账号访问，业务筛选沿用现有报表范围验证。首发支持选项和可受控解析的中文提问。系统先在本地提取允许的指标、门店和日期，再请求模型。无法提取或歧义时请用户通过选项补齐。
2. Django 向 DeepSeek 提供限定的工具。允许调用本期汇总、授权期间或门店对比、已批准制度条款检索。模型看到的是归一化的意图、匿名门店别名和明确期间。业务服务再次校验工具名、参数、循环次数和当前授权，随后执行。
3. 数字由现行报表服务计算。对比时使用同一数据库一致性读取和一次查询截止，按本地营业日解释日期。对「本周对上周」默认采用本周开始至当前本地日期及上周对应天数，界面显示具体区间并允许调整。百分率差以百分点展示。零分母显示不适用，缺项和实际零值分开。
4. 知识检索从已确认的制度与操作说明读取版本、条款编号及摘要，例如 FR-602、FR-603 和预约金退还规则。用版本化的标题、编号及关键词索引即可承接首版知识量。引用保留到批准来源。模型工具得到经过白名单筛选的摘要和汇总；明细、患者信息、病历、过敏和身份资料由 ADC 留存。
5. 结果结构包括期间、范围、截止、核算数字、可观察差异、仍待核实的问题、来源引用和原报表入口。前端用报表数据渲染数字卡片，模型只组织解释。服务端验证返回的指标与来源可回查。复用现有报表缓存，保存与账号范围绑定的本次汇总、截止和下钻凭据。有效期内「查看原报表」显示 Agent 引用的同一汇总和明细，两期分别回查。过期后按原筛选重新查询并明确标注新的截止。快照凭据留在 ADC 内部，每次打开仍重新校验范围。
6. DeepSeek 外部请求在明确启用且连接独立合成演示环境时开放，CI 使用同一适配接口的本地替身。密钥经 Django 服务环境注入。使用留痕只保存账号、请求时间、选中的结构化问题、工具类型、状态及调用量。设置请求计数、超时和成本保护。密钥缺失、超时或模型输出异常时，用同一汇总数据展示模板说明并可查看原报表。

[DeepSeek 工具调用文档](https://api-docs.deepseek.com/guides/tool_calls/)。

## 双店演示与验收

用可重建的本地合成库给两个门店准备正常和异常预约、已签到、结算收退、跨日未决款、不同统计期间、零分母及单店权限。至少有一笔预约贯通网站和小程序的同号查阅。经营演示可用两店各一组完整期间。例如中心门诊从 6/8 变为 4/8，滨江门诊从 2/4 变为 3/4。验收分别校验下降和上升 25 个百分点及原报表分子、分母，实际演示使用与测试一致的合成事实。

| 场景 | 完成条件 |
| --- | --- |
| 业务链 | 小程序预约，前台从带红点的现有入口进入同号预约，签到并分椅，牙医核对过敏并完成治疗，前台模拟开单和收款，患者查看本人诊疗费用。 |
| 待办与导航 | 已有预约、临床、结算或更正入口在存在待办时出现红点。处理后刷新提示。刷新、后退及窄屏操作保留必要上下文。 |
| 权限变更 | 双单店账号结果不同，非法直达被拒。临床和财务业务权与权限后台分离。审计可回查，禁止自我提权及去除最后的有效管理员。 |
| 日结与账单 | 同日不同资金账类分开，迟到回执按成功日归期，跨日未决单独显示。金额与原流水一致。患者查看异主单返回统一未找到。 |
| Agent 正向 | 从可点击问题发起一次真实 DeepSeek 请求。显示同一截止的两店对比、可回查口径和汇总数值，打开同一报表快照，随后提供可选择的下一步。 |
| Agent 反向 | 只有一家门店时隐藏双店建议。模型故障、越权参数、缺数据、零分母、无效来源及随意输入个人信息时按定义交互并保留报表可用。 |
